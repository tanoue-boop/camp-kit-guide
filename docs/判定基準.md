**この文書がすべての判定の唯一の正。** タスク定義は本文書を**全文転記しない**（2026-09-27 の運用組み替えで廃止。転記が原因でタスク定義が129KBまで肥大していた）。タスク定義には**本文書のパスと sha256、およびその回で実際に適用する条文の番号だけを名指しで書く**。条文番号の名指しは要約ではないので、旧ルールの趣旨（監督が要約して意味を変える事故の防止）には反しない。**抜粋・要約・言い換えをして条文の内容をタスク定義に書き写すことは、従来どおり禁止する。**

## 0. 大原則

1. **ページ外の知識を使わない。** 判定に使ってよいのは、実際に取得した dp / 楽天ページに印字されている文字列と、台帳に記録済みの過去の実取得値だけ。モデルが知っている企業関係・ブランド系列・ローマ字転写は一切使わない。（67 §0）
2. **前回の結論を再利用しない。** 同一ブランド・同一店舗でも出品ごとに結論は割れる。「このブランドは前回 official だった」は根拠にならない。（87 §9(3)・91 §4 で実証）
3. **読めないものは倒さない。** 判定材料が無いときは `unknown`。推測で `official` にも `marketplace` にもしない。
4. **新しい verdict 値・新しい issue_type を作らない。** 値域は下記 §3・§4 に固定。（59）
5. **検出器（`check-amazon-asin.cjs` / `check-card-name-vs-sku.cjs` / `verify-deploy.cjs`）の判定・照合・選択SKU の規則を変更しない。** 許されるのは `TASK_ID` の更新と `--test` ケースの追加のみ。変更が必要と思ったら QUESTION に回す。（32）
6. **report の要約数字は、表からではなく TSV から自分で足し直して書く。**（61。39・60・65・68・87・91 で各 1 件、97 で §2 の行番号 1 件の転記ミスが実際に出ている。96・98・99・100・101・103・104 は 0 件）

## 1. `seller_type` の判定

### 1-1. 「dp のブランド欄」の定義（経路①②共通）

1. 商品情報テーブルに `ブランド` 行があれば**その値を第1優先**とする。
2. 無ければ `id='bylineInfo'` のブランドリンクの**表示名**を使う。
3. `bylineInfo` が著者名・出品者名になっているページは「ブランド欄なし」と扱う。
4. プレミアムブランドページは `bylineInfo_feature_div` が空で、ブランドが `id="brandLogoBylineLink"` の `<img alt=…>` に出る。この型は**③の商品情報テーブル値で判定**し、判定表には `NOT_PRESENT（プレミアムbyline alt=…）` の形で両方書く。
5. **判定表には必ず両方を併記**する（存在しない側は `NOT_PRESENT`）。

**`メーカー名` 欄と商品タイトルは、経路①に加えない。**（恒久ルール F）`メーカー名` 欄にはブランド名が入っていることがあり、法人名である保証がない。

### 1-2. 経路①（店舗名とブランド欄の照合）

**成立条件**: 販売元の店舗名から下記を除いた**土台**が、**dp ブランド欄が提示するいずれかの表記そのもの**と literal に一致すること。（恒久ルール E・G）

除いてよいもの:

- **自称・装飾**: `【公式】`・`公式`・`正規販売店`・カギ括弧内の宣伝文言（`【安心の日本セラー☆保証充実】` 等）
- **業態を表す一般名詞**: `Store`／`Shop`／`ショップ`／`ストア`／`直営店`／`専門店`／`オンラインストア`／`Direct`／`Official`／`アマゾン店`
- **法人形態・商流を表す一般名詞**: `International`／`Corporation`／`Corp`／`Trading`／`Commerce`／`Japan`／`株式会社`／`有限会社`
- **国名コード**

**限界（これを外すと①が無制限に緩む）**:

- **除去後の残余が別の固有名を含むなら①不成立。** 例: `五星館株式会社`（ブランド `HAWKGEAR`）は `株式会社` を除いても `五星館` という別法人の固有名が残るので不成立。要求するのは「除去したら一致した」ではなく「**除去後の土台がブランド表記そのもの**」であること。
- **表記体系をまたぐ転写の同定は禁止**（追補4・維持）。ブランド欄が `PYKES PEAK` しか出さないのに店舗名が『パイクスピーク』は**不成立**。ローマ字転写の同定はページ外の知識に当たる。
- **ブランド欄が和名・かなのみを提示しているときに、店舗名の和名側と一致するのは成立**（恒久ルール E）。`トヨトミ(TOYOTOMI)` のように両方提示していれば、和名側との一致でも成立する。
- **英字が複数トークンのとき、一部一致では不成立**（追補2）。`ZEN Camps` に対して店舗名が `ZEN Goods Store` は不成立。
- **`和名(英字)` 形式のブランド欄は、括弧内英字も英字表記とみなす**（追補1）。

### 1-3. 経路②（法人名の並記による同定）

**成立条件**: ブランド名（または法人名）と法人名が、**出品しているという事実とは別の文脈で並記**されていること。成立する場所は、商品情報欄の `メーカー名`、feature-bullets・product-description の本文、ブランドストアリンクの表示名、特商法欄の販売業者欄。

**②の根拠にしてはならない記載（追補5）** — 出品者が「自分が売っている」という事実だけを述べたもの:

- 販売元表示・出荷元／販売者表示（`sellerProfileTriggerId` アンカー周辺）
- 「この商品は、◯◯が販売および発送します。」
- 共有ウィジェット（`id="ssf-primary-widget-desktop"` 等）の `〈商品名〉／〈出品者名〉による` 形式
- 配送ポリシー・返品ポリシーへのリンク文言
- 動画・画像メタの `vendorName`／`publicName`

**これらはブランド名と隣接していても②は不成立。** この例外を認めると、どの商品ページにもある文言が根拠になり、あらゆるマーケットプレイス出品が `official` になって `seller_type` 列の弁別力が 0 になる。

**`メーカー名` 欄の値がブランド名と同一のときは②の根拠として使えない。**

### 1-4. 特商法値の再利用（恒久ルール D）

過去タスクが実取得して台帳に記録した特商法欄の販売業者の値は**再利用してよい**。ただし次の 3 条件をすべて満たすこと。

1. 再利用できるのは、**dp の販売元名が文字列として一致する同一ストア**について記録された値に限る（似た名前・推定での同定は不可）。
2. その値が `amazon-asin-check.tsv` の `note` か `article-fix-backlog.tsv` の `notes` に、**取得したタスクIDつきで記録されている**こと。report には出典（どの行の note か・どのタスクが取得したか）を明記する。
3. **1-3 の除外リストに当たる記載は、過去タスクのものであっても②の根拠にならない。**

### 1-5. 値域

`official`／`marketplace`／`amazon`／`unknown`／`reseller`／（空）。①または②が成立すれば `official`、どちらも不成立なら `marketplace`、材料が無ければ `unknown`。

## 2. 「自称」は根拠にならない

店舗名の `【公式】`・`正規販売店` 等の自称は、それ自体では `official` の根拠にならない（56）。自称を除いた土台で①が成立するなら成立する（追補3）。

## 3. `verdict` の判定

### 3-1. 値域（これ以外を作らない）

`ok`／`model_mismatch`／`different_product`／`out_of_stock`／`404`／`blocked_by_amazon`／`unverifiable`／（空）

### 3-2. 色・サイズの食い違い（51 ＋ 71 §0-3 の 2 段階）

**大原則: カードが軸の値（色・サイズ）を名指ししていなければ `ok`。名指ししている場合にのみ食い違いを採る。**

- **段階1**: 変種一覧に「カードの名指しにより良く当たる別変種」があれば `model_mismatch`。
- **段階2**: 無ければ、着地変種を §1 の基準で見て判断する。
- **色と構成が競合したら構成を優先。**

**名指しとみなさないもの**: ①型番に埋め込まれた色コード（`TT8-583-TN` の `TN`・`P0078CRCK3-BLK-3SET` の `BLK`）②全色の列挙（`BK/TN/KH カラー展開`）③製品名の一部（`オーバーサイズ`・`ロングセラー`）④構成の名指し（`シングル`・`1枚用`・`本体のみ`・`セット`）⑤型番そのもの。

⚠️ **楽天が書いた「対応機器の寸法」をサイズの名指しと読み違えない**（71 の `stove-guard`）。

### 3-3. `different_product` の優先（68 Q1）

**ブランド／型番／色／サイズのうち 2 つ以上が確定的に食い違うなら `different_product` を優先する。**

### 3-4. 出品ゼロ・在庫切れ

- **出品ゼロで変種一覧が取れない行は `out_of_stock`**（66）。
- 「実在するが出品 0 件」は `amazonAsin` を除去するが、**台帳の backlog 行は `pending` 継続**（64）。
- 在庫切れ ASIN は新規採用しない。「在庫切れ」は **Amazon 側**の在庫を指す（20）。

### 3-5. 同一 ASIN でも verdict は分かれてよい（65）

同じ ASIN を複数のカードが指していても、カードの名指しが違えば結論は違ってよい。

### 3-6. `autoVerdict` の死角（人手で覆すべきケース）

**偽の `ok` が出る 3 つの死角**: ①型番が本体とセット品で共通 ②型番が変種間で共通 ③**dp のメーカー型番欄に親 ASIN（ファミリー）の値が入る**。いずれも「型番一致は着地変種の正しさを保証しない」という同じ話。確実な手当ては保存 dp HTML の `dimensionValuesDisplayData` を JSON として読むこと。

**偽の `unverifiable` も大量に出る**（カード name に型番トークンが無いだけ）。①dp メーカー型番と楽天商品コードの一致 ②変種一覧の着地値 ③dp の仕様欄 の 3 系統で追認できる。

## 4. ASIN を採用してよいかの判定

### 4-1. 恒久ルール (A) — セット構成

**カード name が同梱物・セット構成を明示的に名指ししている場合、同梱物の異なる ASIN は「本体が同一」でも採用しない。** とくに**単品側のほうが高い**ときは例外を認めない（読者が気づかないまま割高に買うため、404 より害が大きい）。

**★ この条文は楽天 URL の差し替えにも及ぶ。単品側が安い場合も差し替え不可。詳細は §11-9。**（98 §QUESTION-1 の回答）

### 4-2. 恒久ルール (B) — 無名 OEM

**楽天側・Amazon 側の双方でブランド欄が実質空（「なし」「ノーブランド品」「-」）で、かつ型番が店舗 SKU コードしか無い商品は、スペック文の一致だけでは採用しない。**

採用してよいのは、次のうち**少なくとも 1 つが成立する**場合に限る:
①ブランド欄の値が両側で一致 ②メーカー型番が両側で一致 ③カードが名指しする色・サイズ・構成が dp で確認できる

**★ 適用順序（99 §QUESTION-1 の回答・2026-09-24 14:55 追記）: §4-2 と §11-1 は「候補として採ってよいか」を決めるゲートであり、§11-2・§11-3 は「ゲートを通った候補のどれを選ぶか」を決める選択規則である。必ずゲートを先に適用する。** したがって **§11-3 の「同一商品の楽天最安」の母数は、§11-1／§4-2 で同一商品と確定した出品だけ**である。同一性が確定していない安い出品を母数に入れて +20% を計算してはならない（99 の T5 がこの取り違えで噛み合わなくなった）。

#### ★追補1（104 §QUESTION-1 の回答・2026-09-26 22:55 新設）— 無名 OEM カードへの Amazon 新規追加は「dp 予算とセット」でのみ対象に含める

**回答: (A) を採る。すなわち「無名 OEM カードを対象に入れる回は `/s` 予算と dp 予算をセットで付ける」。ただし dp を投機的に使わせない。**

**論点の確認**: (B) のゲート①②は、無名 OEM の定義そのもの（双方でブランド欄が実質空・型番が店舗 SKU しか無い）により**定義上つねに不成立**である。残るのはゲート③だけで、③は文言どおり **dp を開くことを要求する**。したがって **`/s` 予算しか無いタスクでは、無名 OEM カードへの Amazon 新規追加は構造的に 1 枚も成立しない。** 104 の `kids-sleeping-bag#3・#4・#5` はこの理由で全滅した。とくに `#5` は**カード `name` から `送料無料` を除いた文字列が候補タイトルと文字単位で一致し、価格も ¥1,298 で完全一致**していたのに採れなかった。これは条文の欠落であって、実行側の判断の誤りではない。

**条文**:

1. **監督は投入前に、Amazon 新規追加の対象カードを 2 型に分けて、タスク定義にどちらかを明記する。**
   - **型I（実在ブランド＋型番）**: カード `name` にブランド語と型番トークンが印字されている。→ **`/s` 予算のみで対象に入れてよい**（ゲート①②が成立しうる）。
   - **型II（無名 OEM）**: 楽天側の `ブランド名`／`メーカー型番` が `-`・`なし`・`ノーブランド品` のいずれか、または型番が店舗 SKU しか無い。→ **`/s` 予算に加えて dp 予算を付けない限り、対象に入れてはならない。**
2. **型II を対象に入れる回は、D-6 に「`/s` N 回」と「dp M 件」の両方を数字で書く。** dp は 90 秒制約の対象なので、所要見積りに必ず入れる。
3. **dp を投機的に開かせない。** 型II のカードで dp を開いてよいのは、`/s` の**広告でない**結果カードに、次の 2 つが**ともに**成立する候補があるときだけ。
   - カード `name` から販促語（`送料無料`・`ポイント`・`半額`・`先着`・`CP` 等）を除いた文字列が、候補タイトルと**文字単位で一致**する
   - 候補の Amazon 価格がカード `price` と **±3% 以内**
   この 2 つを満たす候補が 1 件も無ければ **dp を開かず**、そのカードは**採用不可として mdx 不変更で終える**。`amazon-backfill-no-amazon.tsv` には書かない（起票は監督が行う）。
4. **同題・同価格の候補が 2 件以上あるときは、両方の dp を開いて `dimensionValuesDisplayData`・`メーカー型番`・`品番・型番`・`販売元` を突き合わせ、一意に決まらなければ採用しない**（§11-6 の「一意に特定できない出品は採らない」と同じ趣旨）。この型は dp 2 件が必要なので、監督は D-6 に 2 件と書く。
5. **ゲート③の充足は dp に印字されている値だけで判断する**（§0-1）。カードが色・サイズ・構成のいずれかを名指ししているならその値を dp で確認する。名指しが 1 つも無いカードは、**「dp の変種が単一である」ことを確認した場合に限り**③を満たす。**名指しが無いことを理由に③を「確認不要」として通してはならない。**
6. **型II なのに dp 予算が付いていない回で `/s` を投げてしまった場合は、そのカードを採用不可で終え、report に「dp 予算なしのため③を満たしようがなかった」と明記する。** 監督は次回に dp 予算を付けて再投下する。**この状態を「Amazon に同等品なし」と読んではならない。**

7. **§4-2 追補1 条文7（第105回に新設）— 「`ブランド名` が `-` だが `メーカー型番` に実値がある」型の扱い。** 楽天側の `ブランド名` が `-`・`なし`・`ノーブランド品` のいずれかで、かつ `メーカー型番` に実値が印字されている出品は、条文1 の「or」により **型II として扱う**（ゲート③の文字単位一致ゲートを当てる）。ただしこの型ではゲート②（型番の両側一致）が原理的に成立しうるので、**`/s` の結果に当該型番の literal 印字があるかを必ず確認し、その実測件数を report に書く。** 印字が 0 件なら採用不可として mdx 不変更で終える。実例: `day-camp-tent#1`（`ブランド名` = `-`／`メーカー型番` = `TNT-200`。`campkit-20261001-M02` が型II として扱い、型番の印字 0 件で採用不可とした。監督はこれを正とした）。**なお `メーカー型番` の値が店舗の商品コードと同一のときは §11-11 により識別子として扱わない。**

8. **§4-2 追補1 条文8（第107回に新設）— 条文2〜6 の dp 開放条件は型II（および追補3 の型I-b）専用である。型I に当ててはならない。** 条文3 の「カード `name` から販促語を除いた文字列が候補タイトルと文字単位で一致」「Amazon 価格がカード `price` と ±3% 以内」の 2 条件は、**ブランドが一切印字されていないカードを前提に組んだ強さ**である。**型I（楽天側にブランド語と型番が印字されているカード）では、Amazon 候補の価格乖離は dp を開かない理由にならない。** 型I の採否は §4-2 の ①②③ と §4-3 追補3（型番ラベル 3 系統の等価）で決める。実例: `day-camp-tent#3`（楽天 コールマン公式店 `coleman/col5767`・カード `name` にブランド語 `コールマン` と型番 `2254415` が印字）に対し `campkit-20261001-03` が条文3 の ±3% を当て、有力候補 `B0GQZ273Y9`（−8.1%）の dp を開かずに終えた。**条文の射程の読み違いであり、実行側の判断の誤りではない。** `campkit-20261001-05` が dp 予算を付けて再投下した。

### §4-2 追補4 — `ブランド` 欄の字面ゆれの扱い（第86回に新設）

§4-2 追補3 の 4.① および §4-3 追補4 の 4.① の「dp の `ブランド` 欄が楽天の `ブランド名` 欄と一致する」は、**次の 1.〜5. をすべて満たす場合にかぎり、字面が完全一致しなくても「一致する」と読む。** 1 つでも欠けたら不成立とし、非採用にする。

1. **正規化は 2 種類だけ許す。** (i) 全角英数字・全角記号を半角へ、(ii) 英字の大文字小文字を無視する。**それ以外の変換（空白の除去・記号の除去・カタカナ化・略記の展開）は行わない。**
1-a. **（111 §QUESTION-1 の回答・第87回に追加）** 1.(i) の「全角→半角」には **U+3000（IDEOGRAPHIC SPACE・全角空白）→ U+0020（半角空白）** の変換を**含める**。これは空白の「**除去**」ではなく「**変換**」であり、1. が禁じる正規化には当たらない（文字数は保存される）。したがって dp の `ブランド` 欄が全角空白で区切られている場合も、2. のトークン分割は正常に働く。**この解釈を採らないと、下記「第86回の適用例」（`Ｒｅ　Ｒｅ：Ｇｅａｒ` → `["Re","Re:Gear"]`・区切りは実測で U+3000）が成立しなくなる。**
2. 正規化後の dp `ブランド` 欄を**半角空白で分割**したとき、**楽天の `ブランド名` 欄の値（同じ正規化を通したもの）が、トークンの 1 つと完全一致する**こと。部分文字列としての出現では足りない。
3. 残りのトークンは**すべて**、2. で一致したブランド語の**真の前方一致（prefix）または真の後方一致（suffix）**であること。**ブランド語に含まれない語が 1 つでもあれば不成立。**
4. 楽天の `ブランド名` 欄の値が**2 文字以上**であること（1 文字のブランド語では 3. が意味を持たないため）。
5. **候補タイトルにブランド語の literal 印字がある**こと（§4-2 追補3 の 3.(a) のゲートを既に通っていること）。

6. **§4-2 追補4 条文6（第99回に新設）— 逆向き（楽天側が複数トークン）の場合。** 楽天の `ブランド名` 欄の値が `英字（カナ）` の形（実例: `AETONYX （アエトニクス）`）のときは、1. の正規化（1-a. を含む）を通したうえで、**半角空白・全角および半角の丸括弧（`（`・`）`・`(`・`)`）を区切りとして分割**し、得られたトークンのいずれか1つが dp の `ブランド` 欄の値（同じ正規化を通したもの）と**完全一致**する場合も 4.① 成立と読む。ただし次の (a)〜(c) をすべて満たすこと。1つでも欠けたら不成立とし、非採用にする。
   - (a) 一致したトークンが **2 文字以上**であること（4. と同趣旨）。
   - (b) 残りのトークンが**すべて**、(i) 一致したトークンの真の前方一致または真の後方一致か、(ii) **カタカナのみで構成される語**（＝ブランド語の読み）のいずれかであること。**それ以外の語が1つでもあれば不成立。**
   - (c) 候補タイトルに、一致したトークンの literal 印字があること（5. と同趣旨）。

### 4-4. ★ `amzn.to` 短縮リンクの展開は「判定」ではない（2026-09-24 16:10 新設）

**`link_form=amazonUrl`（`amzn.to` 短縮）のカードを `amazonAsin` へ展開する操作は、リダイレクト先の dp を読み取って同じ着地先を別形式で書き直すだけであり、読者の着地先を 1 文字も変えない。** したがって §4-1・§4-2 の採否判定は要らない。

5. 展開は §6 により**凍結記事でも可**。

⚠️ **着地 URL が `/<タイトルスラッグ>/dp/<ASIN>?…` の形（検索結果経由で発行された短縮リンク）でも、着地先が単一商品の dp である限り要件1 を満たす**（103 の `lantern-carry-medium` で実例。クエリに `keywords=`／`sr=8-1` が残っているのは発行経路の痕跡にすぎない）。

#### ★追補1（監督の実測・2026-09-24 18:05 新設）— `both_forms`（両属性を持つカード）は §4-4 の射程外

**§4-4 の大前提「展開は読者の着地先を 1 文字も変えない」は、`amazonUrl` と `amazonAsin` を両方持つカード（`static_flags` に `both_forms`）には当たらない。**

根拠（監督が clone 上で実測）— `components/article/ProductCard.tsx`:

```
25:  if (product.amazonUrl) return product.amazonUrl;
26:  if (product.amazonAsin) return buildAmazonUrl(product.amazonAsin);
```

**`amazonUrl` が `amazonAsin` より優先される。** したがって `both_forms` カードでは、

- 読者が実際に飛ぶ先は **`amzn.to` の側**であり、`amazonAsin` は**書いてあるだけで使われていない**。
- **`amazonUrl` を削除すると、読者の着地先が `amazonAsin` の側へ移る。** 両者が同じ ASIN を指している保証は無い。
- 台帳の `asin` 列は `amazonAsin` の値だが `amazon_url` 列は `amzn.to` のままなので、**判定済み ASIN と実際の着地先が一致している保証も無い**。

**処置（必ずこの手順による）**:

1. `amzn.to` の Location を辿って ASIN を取り出す（§4-4-1 と同じ。dp 本体は開かない）。
2. **取り出した ASIN と、そのカードの既存 `amazonAsin` を突き合わせる。**
   - **一致** → `amazonUrl` 属性**だけ**を削除する（`amazonAsin` は据え置き・値を書き換えない）。着地先が変わらないので §4-4 の射程内。
   - **不一致** → **追補3 の要件が成立するかを見る。成立しなければ何も書き換えず据え置く。** 両方の値（既存 `amazonAsin` / 展開で得た ASIN / 最終 URL 全文）を report に書いて、そのカードの処置を打ち切る。
3. どちらの枝に入ったかを、カードごとに report の表に書く。

**実証（103）**: `soto-burner#2#soto-st310` は既存 `amazonAsin=B077Q99XBS`・展開 ASIN `B001ADSR56` で不一致だった。**機械的に `amazonUrl` を削除していれば、カード `name` が名指しする標準 ST-310（`B001ADSR56`）を捨てて Amazon 限定モノトーン（`B077Q99XBS`）へ読者を移していた。** 追補1 が事故を止めた実例である。

#### ★追補2（監督判断・2026-09-26 21:05 新設）— 一度 `done` にした `discontinued_404` 行のカードが再び 404 になった場合

**新規行を起票せず、その既存行に追記する。** §5-2 の「同一カード・同一 `issue_type` の既存行があれば新規起票せず `notes` に追記」（72 §0-8）が優先する。

**理由**: キーは `target_slug` + `position` + `issue_type` の 3 点（§8）なので、同じ 3 点の行を 2 本作ると以後の突合がどちらを掴むか決まらない。差し替えの履歴は `notes` に `｜` 区切りで積む（既存を 1 文字も削らない）。

**`status` の決め方**:

- 差し替えが**成立した** → `done` のまま（`notes` に今回の差し替えを追記）
- 差し替えが**成立しなかった**（型(c)）→ **凍結記事は `blocked`／非凍結記事は `needs-human`** に戻す。**`done` のまま残してはならない**（リンクが現に死んでいるため）
- `position` 列は**既存の文字列を 1 文字も変えない**（§8 の「`（id: …）` を持たない行」を壊さないため）。差し替え後の商品名は `notes` 側に書く
- `priority` は引き下げない（§5-4）

### 5-3. `status` の決め方

- **`blocked` は frozen slug 専用**（60）。frozen 記事への**新規起票**は必ず `blocked`。
- **★追補（2026-09-24 13:15・97 の検品で確定）: 凍結記事の行でも、§6 で許された範囲（`affiliateUrl`・`price`・Amazon リンク）の修正が実際に成立したら `status` は `done` にする。** §6 改定でリンク差し替えが凍結中でも実施できる以上、`blocked`（＝凍結ゆえ着手できない）は実態と合わない。`notes` の末尾に「（凍結記事・§6 によりリンクと price のみ変更）」を添えること。**成立しなかった凍結記事の行は `blocked` のまま据え置く**（`needs-human` にもしない）。

### 5-4. `priority`

### 5-5. `notes` の扱い

#### ★追補1（108 §QUESTION-1 の回答・2026-09-27 03:55 新設）— 既判定行を `--only` で再判定する回に、人手 `verdict` を書き戻すか否かの切り分け

**回答: 「対象行の `asin` が、その人手 `verdict` を下した時点の ASIN から変わっているか」で決める。**

**論点の確認**: §8 本文は「`--only` は既判定行の人手 `verdict`・`seller_type`・`note` を auto で上書きするので、退避して**書き戻す**」と定めている。しかし 106 の枝 A のように**行の `asin` そのものが入れ替わった**あとでは、旧判定は現在の `asin` を表していない。ここで書き戻すと、**別の ASIN に対する判定を現 ASIN の判定として台帳に残す**ことになり、§8 が守ろうとしている「人手判断の保全」とは逆の結果になる。一方で §4-4 追補5 共通の守り2 は「判定列を手で書かない」と定めており、実行側から見ると 2 条が衝突して見える。両者は衝突していない。§8 は**保全**の条文、追補5 は**創作の禁止**の条文であり、切り分けの軸は「旧判定が現 `asin` を表しているか」である。

**条文**:

1. **`asin` が変わっていない** → §8 本文どおり。実行前に `git show HEAD:_file/amazon-asin-check.tsv` で退避し、実行後に人手 `verdict`・`seller_type`・`note` を**書き戻す**。
2. **`asin` が変わっている**（＝旧判定は現在の `asin` を表していない） → **書き戻さない。** auto の値を残し、退避した旧行の**全 21 列を report に verbatim 転記する**。旧判定は「無効になった判定」であって「保全すべき人手判断」ではない。
3. **1. か 2. か判別できない**（台帳の `note`・`judged_task`・当該タスクの result のいずれからも、旧判定がどの ASIN に対するものか確定できない） → **保全側（1.）に倒して書き戻し**、report に「判別不能のため保全側に倒した」と明記する。**推測で 2. に倒してはならない**（§0-1）。
4. **判別の材料は、台帳の `note` 冒頭のタスクID・`judged_task` 列・当該タスクの result に限る。** ページ外の知識・モデルの推測は使わない。
5. **監督は投入時に、対象行ごとに 1.〜3. のどれに当たるかをタスク定義に明記する。** 実行側にその場で切り分けさせない（切り分けには過去 result の読み込みが要り、無人実行の所要が読めなくなる）。
6. **2. に当たる行を再判定した回は、`verdict` が `ok` 以外になっても mdx を触らない**（§4-4 追補5 共通の守り4 と同じ扱い）。処置は次タスクで監督が設計する。

#### ★追補2（108 §QUESTION-2 の回答・2026-09-27 03:55 新設）— `amazon-asin-check.tsv` の `note` に旧判定の根拠を残す義務

## 11. ★ 楽天リンクの差し替え先の選び方

95〜100 の QUESTION で確定した条文。**`discontinued_404` の差し替えも、記事単位の処理での差し替えも、本節に従う。**

### 11-1. 差し替えの型

| 型 | 内容 | 処置 |
|---|---|---|
| **(a)** 同一商品が**同じ店に別 URL**である | 商品コードの桁違い・出品し直し | `affiliateUrl` を新 URL の `hb.afl` 形式に差し替える |
| **(b)** 同一商品が**別の店**にある | | 同上。店舗の選び方は 11-2 |
| **(c)** 楽天の**どこにも無い** | 廃番・完売 | `affiliateUrl` は触らず `status=needs-human` に倒す（§5-3。凍結記事は `blocked`）。**除去だけで終える操作は禁止** |

**同一商品と判断してよい条件**: ブランド名が一致し、かつ型番または商品名の主要スペック（サイズ・容量・人数・色）が一致すること。**価格だけの一致では同一と判断しない。**

### 11-2. 店舗の優先順位

1. **メーカー公式店**
2. **大手**（`naturum`／`naturum-outdoor`／`himaraya`／`a-price`／`jism`／`kojitu`／`alpen`／`r-kojima`／`biccamera`／`yamada-denki`／`ksdenki` 等）
3. **個人店**

### 11-3. +20% 例外（96 §QUESTION-1 の回答で①にも拡張）

**①または②を採ると、同一商品の楽天最安より +20% を超える**場合は、**その段を飛ばして最安の店を採る**。例外は優先順位のどの段にも掛かる。趣旨は「**同一商品で著しく高いリンク先へ読者を送らない**」こと。

飛ばした先の店は次をすべて満たすこと。満たす店が無ければ、条件を満たす中で最も安い店。それも無ければ元の段のまま据え置き、report に書く。

- 在庫あり
- 商品コードに ASIN 由来文字列（`b0`＋英数字を含む形）を含まない
- **バリエーション選択式でない**（単独出品）

**最安が複数店で同額のときのタイブレーク**: ①**型(a)（死んだ URL と同じ店の出し直し）** → ②**レビュー件数が多い** → ③**レビュー平均が高い**。

**型(a) を優先順位より上には置かない。** タイブレークの第 1 位としてのみ使う。

#### ★追補（99 §QUESTION-2 の回答）— 段を飛ばしたあとも、残りの段の優先順位は生きている

**+20% 例外で捨てるのは「その段」だけであって、§11-2 の優先順位そのものではない。** 手順は次のとおり。

1. **母数を作る**: §11-1／§4-2 のゲートを通った（＝同一商品と確定した）在庫あり出品だけを集め、その中の最安価格を「同一商品の楽天最安」とする。
2. **段①**: 段①の最安が「同一商品の楽天最安」の +20% 以内なら段①を採る。超えるなら段①を飛ばす。
3. **段②**: 段②の最安について同じ判定を繰り返す。+20% 以内なら**段②を採る**。超えるなら飛ばす。
4. **段③**: 同上。
5. **どの段も +20% を超える場合に限り**、全体の最安を採る。

**趣旨**: 個人店の URL は 3 ヶ月で 40 枚＝年 1 割強のペースで 404 になる（キュー#5）。+20% 例外は「著しく高いリンク先へ送らない」ための安全弁であって、**わずかな差額で大手を飛び越して無レビューの個人店へ落とすための条文ではない**。

#### ★追補2（100 §QUESTION-2 の回答）— 段①の価格が当該タスクの検索結果に現れなかった場合

1. **段①専用クエリを 1 本追加で投げる。** 検索語は `<ブランド名> 公式 <商品名／型番>` の形。**楽天 API の回数予算に数える。**
2. それでも段①の出品が **0 件**なら、その商品について段①は「**該当出品なし**」であって「+20% 超で飛ばした」ではない。+20% 判定を掛けずに段②へ進む。**投げたクエリ全文と 0 件だった事実を report に書く。**
3. **同一商品の別店舗で同額の出品が複数あっても、その額を段①の推定価格として扱わない。**
4. **前タスクの実測値の再利用は、出典を明記した参考値としてのみ report に書いてよい。判定の根拠にはしない**（§0-2）。価格は日次で動く。
5. **(c)「確認不能として段①を飛ばす」は不可。**

### 11-4. 同一運営の複数店は「別の店」として扱う（97 §QUESTION-1 の回答）

**`naturum` と `naturum-outdoor` は別の店として扱い、レビューを合算しない。** 「同一運営である」は §0-1 が禁じるページ外の知識に当たる。他の系列店も同じ扱い。

### 11-5. 「入荷予定」表記の出品（97 §QUESTION-2 の回答）

**楽天 API の `availability=1` とページの `InStock` を満たすなら「在庫あり」として扱ってよい。** 文言だけを理由に除外しない（§0-3）。**ただし、同一商品に即納の出品があり、かつ価格差が +20% 以内なら即納側を優先する。** 本条文を適用した行は「入荷予定表記あり・即納は +N%」と明記する。

### 11-6. 採らない出品

- **バリエーション選択式**（1 ページで複数モデルを選ばせる出品）。判定は item ページの `axisName` が **0 個**であることで行う。
- **`【中古】` 表記の出品**。
- 商品コードに **ASIN 由来文字列**を持つ店は、同条件なら最後に回す。他に候補が無ければ採用してよい。
- **タイトルが 2 つ以上のサイズ・仕様を併記していて、カードが名指しする 1 仕様を一意に特定できない出品**。
- **レンタル出品・グランドシート等の付属品単体。**

#### ★追補（107 §QUESTION-2 の回答・2026-09-27 02:35 新設）— 「バリエーション選択式は採らない」は、商品そのものを差し替える場面では条件つきで緩める

**回答: 同じ強さでは掛からない。ただし無条件に緩めない。**

**理由**: §11-6 の当該条項が防いでいるのは「**カードが名指しする 1 仕様と、読者が実際に選ぶ変種が食い違うこと**」である。既存カードの楽天リンクを差し替える場面ではカード `name` を書き換えられないので、名指しと着地の一致を出品側の構造（軸が 0 個）に求めるしかない。**商品そのものを差し替える場面では `name` を自分で書くので、名指しを出品の軸値に合わせて固定できる。** この場合に限り、構造ではなく `name` の書き方で同じ保護が得られる。

**条文**:

- **(a) 既存カードの楽天リンクの差し替え（§11-1 の型 (a)(b)）では §11-6 のまま。** また **凍結記事では カード `name` を書き換えられない（§6）ので、商品差し替えの場面であっても §11-6 のまま**とする。
- **(b) 商品そのものを差し替える場面（非凍結記事・`name` を書き換える回）では、次の 5 条件をすべて満たす場合に限り、バリエーション選択式の出品を採用してよい。**
  1. **軸の値を全件実測して report に列挙する**（`variantSelectors` の軸名・全軸値・各値の価格・在庫・`メーカー型番`）。
  2. **採用する値を軸ごとに 1 つに固定し、カード `name` にその値を literal で書く**（`CLAUDE.md` の「バリエーション商品は `name` にカラー／サイズ／容量を必ず含める」の運用に一致させる）。
  3. **固定した値が在庫あり**（`InStock` かつ当該 variant の在庫数が 0 でない）であること。
  4. **カード `price` は固定した値の価格を書く。** 価格帯の `lowPrice` をそのまま書いてはならない。**その価格が記事内でその枠が担っている役割（最安枠・比較表・まとめ表の価格帯表記・`badge`）と両立することを確認する。**
  5. **軸が記事テーマの軸（容量・サイズ・人数など）を含み、かつ記事テーマ外のモデルを同一ページで選ばせる出品は採用しない。** この場合は §11-6 のまま落とす。
- **`reviewCount`／`reviewAverage` は item ページ単位の値であって、固定した変種のものではない。** 採用時に `rakutenRating`／`rakutenReviewCount` へ item ページの値を書くのは可とするが、**本文・`badge` でその数値を「その仕様の評価」として書いてはならない**（§11-8 と同じ性質）。
- **(b) を使って採用した場合は、5 条件それぞれの充足を report に 1 条ずつ書く。** まとめて「条件を満たす」と書いてはならない。

**適用（107・事後承認）**: Naturehike `cnk2550xb018`（`https://item.rakuten.co.jp/naturehike-direct/cnk2550xb018/`）は、軸が `サイズ`（`30（M）`／`45（M）`／`45（L）`／`60（M）`／`60（L）`）・`カラー`（`白`／`黒`）の 2 軸で、**30L 記事のテーマ外である 45L・60L を同一ページで選ばせる出品**であるため **(b)-5 に該当し、本追補のもとでも採用できない。** また ¥9,900 は当該枠（最安枠・まとめ表「6,000円台」）の役割と両立しない（(b)-4 不成立）。**107 の落選判断は正しい。差し戻さない。**

### 11-7. アフィリエイト ID（95 §QUESTION-1 の回答）

- **差し替え・新規の `affiliateUrl` は `.env.local` の `NEXT_PUBLIC_RAKUTEN_AFFILIATE_ID` を使う。** `&m=`／`&rafcid=` は付けない。
- 既存カードに残る**店舗別の旧世代 ID（927 本・228 種）は触らない**（キュー#60）。
- 差し替える行は新規発行扱いなので、旧世代 ID から env の値に**更新してよい**。

### 11-8. 差し替え後に触らないもの

- **`rakutenRating`／`rakutenReviewCount`／`badge`／`image` は据え置く**（キュー#61・#62）。
- **`price` は差し替え先 SKU の現価と ±3% を超えて乖離したときだけ更新する。** ただし**同一商品を指す複数カード（組）は、組内で値を揃えることを優先する**。
- **比較表（`ComparisonTableMdx` の `rows`）の `affiliateUrl` はカード側と自動追随しない。** 死んだ URL が残るので、行番号つきで report に列挙させる（修正はさせない。キュー#63）。

### 11-9. ★ セット構成を名指しするカードの差し替え（98 §QUESTION-1 の回答）

**回答: 差し替え不可。単品側が安い場合も不可。** §4-1 恒久ルール (A) は楽天 URL の差し替えにも及ぶ。

**処置**: この型は **§11-1 の (c) として扱う**。非凍結記事は `status=needs-human`、凍結記事は `blocked` のまま据え置き。

**例外は 1 つだけ**: 記事単位フェーズで、**同一タスクの中でカードの `name`・`description`・見出し・本文・比較表・まとめ表まで新構成に合わせて直せる場合**は、**商品差し替え案件**として実施してよい。凍結記事はこれができないので据え置く。

### 11-10. ★ 型番が異なる同ブランド品への差し替え（98 §QUESTION-2 の回答）

**回答: 可。ただし下記 5 要件をすべて満たすときに限る。**

1. カード `name` に**型番トークンが存在しない**こと。**存在するのに別型番へ差し替えるのは不可**（その場合は型(c)）。
2. カード `name` の**数値スペックがすべて**差し替え先ページに印字されていること。**1 つでも欠けたら採らない。**
3. 数値以外のトークンの不一致は、**同義語がページに印字されている場合に限り**許容する。**ページに無い語を補って同義と判断しない**（§0-1）。
4. **旧型番が `availability=1` の検索で 1 件もヒットしない**こと。
5. **段①（メーカー公式店）であること。**

**`price` の乖離幅は可否に影響しない。** ただし **±30% を超えて動かす場合は、台帳 `price_gap` の差し替え前後の値を report に書く。**

### 11-11. ★ 楽天の商品管理番号（URL slug）の一致の扱い（99 §QUESTION-1 の回答）

**回答: 同一商品の根拠にしてはならない。** 店舗が自分で付ける値であり、**§4-2 (B) の②「メーカー型番が両側で一致」には当たらない。**

**例外は 1 つだけ**: §11-1 型(a)（**同一店舗**での出し直し）の同定に使う場合。

**ただしタイブレークには使ってよい**（別の根拠でゲートを通った候補が同点のとき）。

### 11-12. ★ カード `price` と候補価格の乖離は、同一性を否定する根拠にならない（99 §QUESTION-1(c) の回答）

**価格を同一性の根拠に使えない以上、価格を同一性の否定にも使えない。** 乖離が大きいときに行うのは「候補を落とすこと」ではなく、「**同一性の根拠をもう一度確認したうえで、乖離幅と `price_gap` の前後値を report に書くこと**」。

### 11-13. ★ カード `name` が名指しする色だけが楽天から消えている場合（100 §QUESTION-1 の回答）

**回答: (A) と (B) の両方が正。どちらになるかは「そのタスクでカードの表示テキストを直せるか」で決まる。**

**(A) リンクだけを直す回: 別色へ差し替えない。型(c) とする。** 凍結記事は常に (A)（`blocked` 据え置き）。非凍結記事は `needs-human` に倒し、**記事単位フェーズで (B) として拾う案件**であることを `notes` に書く。

**(B) 記事単位フェーズで、同一タスクの中でカードの `name`・`description`・見出し・本文・比較表・まとめ表の色表記まで直しきれる場合: 同一商品ラインの別色へ差し替えてよい**（非凍結記事に限る）。

要件（すべて満たすこと）:

1. **ブランド名が一致**していること。
2. **色以外の主要スペック**が、差し替え先ページに**印字されている**こと。1 つでも欠けたら採らない。
3. **旧色が `availability=1` の検索で 1 件もヒットしない**こと。色名を入れたクエリを最低 2 本投げ、全クエリと全件を report に列挙する。
4. 差し替え先の店は **§11-2 の優先順位と §11-3 に従って選ぶ**。
5. **カード `name`・`description`・見出し・本文・比較表・まとめ表の色表記を、差し替え先ページに印字されている色名へ直す。** `4色選択可能` のような色数の記述も、実際に印字で確認できる色数に合わせる（§0-1）。
6. `image` は §11-8 により据え置き。ただし**色を直した回は `image` の色と本文の色が食い違うので、行を report に列挙する**。

### 11-14. ★ 楽天のブランド欄が `-` の商品は、店舗名由来の語をカード `name` の先頭に書かない（104 §QUESTION-2 の回答・2026-09-26 22:55 新設）

**回答: このルールを足す。**

**根拠（104 の実測）**: `kids-sleeping-bag#3` のカード `name` は `GHCアウトドア 寝袋 …` で始まるが、**`GHCアウトドア` は楽天のブランド索引に存在しない**。単独クエリで 20 件ヒットするが**すべて GOHEMP の型番文字列 `GHC****` への部分一致**（Tシャツ・パンツ・SDカード・中古パーカー）で、寝袋は 1 件も出ない。元の出品ページの店舗コードが `ghc-shop` であることとの一致から、**店舗名由来の擬似ブランド**である可能性が高い。その結果、リンクが 404 になったあとの再探索で**ブランド軸の手掛かりが 1 つも使えず**、14 クエリを投げても同一商品に到達できず型(c) が確定した。**カード `name` の先頭語は、再探索のときに唯一の検索軸になる。** ここに索引に無い語を置くと、その商品は事実上復旧不能になる。

**条文**:

## 12. ★ Amazon `/s` 検索の取得手段（101 §QUESTION-3 の回答・2026-09-24 18:05 新設）

**Claude in Chrome が使えるセッションではそれを使う。使えないセッション（定期タスクの無人実行はこちらが通常）では、スクリプト経由の `/s` 取得を正規の手段として認める。**

従来「スクリプトからの `/s` は Akamai の `bm-verify` に弾かれる」としていたが、101 が実測で切り分けた結果、**2 クエリとも HTTP 200・1.0MB / 2.3MB・`<title>` 正常・ボットチェックの痕跡なし**で取得できた。前提は少なくともこの環境では成立していない。**ただし 103 では 4 クエリのうち 1 本が、104 では 5 クエリのうち 1 本が `bm-verify` で落ちた。通ることは保証されない。**

⚠️ **`claude/campkit-商品選定フロー-決定版.md` ステップ 4 の「スクリプトからの `/s` 検索は使わない」は本節より古い。本節が優先する。**

### 12-1. 守ること

1. **無人実行の間隔は 90 秒を維持する。** 弾かれる条件（IP・頻度・UA）は変わりうるので、間隔を詰めて確かめない。
2. **取得した HTML を `_file/_work/` に保存する**（gitignore 対象・コミットしない）。再検証をネットに出ずに行えるようにする。
3. **クエリごとに次の 5 項目を report に書く**: HTTP ステータス／バイト数／`<title>`／`data-asin` の件数／**広告でない検索結果カードの件数**。

### 12-2. 検知して止める（4 シグナル）

次のいずれかを検知したら、**そのクエリの結果を使わず、停止して報告する**。

- `bm-verify`
- `Robot Check`
- `api-services-support@amazon.com`
- `自動アクセス`

⚠️ **偽陽性が既知**（57 の先例: 正規 404 ページの HTML コメントに `自動アクセス` が含まれる）。検知したら「弾かれた」と断定せず、**検知した文字列とその前後を verbatim で引用して報告する**。

**真のインタースティシャルの見分け方（103・104 の実測）**: 応答が **2,282〜2,788 バイト**（正常な `/s` は 0.7〜2.7MB）・`<title>` が `&nbsp;`・`<meta http-equiv="refresh" content="5; URL='…&bm-verify=<トークン>'">` の構造・`data-asin` 0 件。この 4 点が揃えば真のブロックと判断してよい。

### 12-3. ★ 5 つ目のゲート — 「200 で中身が空」は「出品なし」ではない

**弾かれ方はインタースティシャルだけではない。200 を返しながら中身を空にする形のソフトブロックがあり、これは 12-2 の 4 シグナルのどれにも掛からない。**

したがって:

- **HTTP 200・4 シグナルなしでも、広告でない検索結果カードが 0 件なら、「Amazon に出品が存在しない」と結論してはならない。** `判定不能` として報告し、**§4-3 追補の言い換え 1 本に進む**。
- **言い換えも同じ状態なら、そこで停止して報告する。** `no-amazon.tsv` への起票は監督が行う（実行側は D-10 により触らない）。
- **4 シグナルの検知は停止の十分条件だが、非検知は続行の十分条件ではない。**

**0 件が自分のパーサの偽陽性でないことを保存 HTML で確認する手順（103 が実施・104 が追認・以後必須）**: ①Amazon 自身の `<h2>検索クエリに一致する結果はありません。</h2>` の有無 ②`s-metadata` の `{"totalResultCount":N,"asinOnPageCount":N,…}` 宣言 ③検出した `data-asin` が `class="… AdHolder …"` の内側かどうか ④型番・ブランド語の印字がクエリのエコー（`<title>`／`twotabsearchtextbox` の `value`／nav の戻り URL／`s-metadata` の `keywords`）だけかどうか。

### 12-4. ★ ソフトブロック／4 シグナルで取得できなかったカードの扱い（103 §QUESTION-2 の回答・2026-09-26 21:05 新設）

**回答: 別タスク回での再試行を認める。** §12-1-1 の「間隔を詰めて確かめない」は**同一実行内で待機間隔を短縮すること**を禁じた条文であり、日をまたいだ別タスクでの 1 回の再取得はこれに当たらない。

1. **再試行は 1 カードにつきタスク 2 回まで**（初回＋再試行 1 回）。2 回目も 4 シグナルまたは §12-3 の空応答なら、そのカードは**監督の保留案件**に移し、以後自動で再投下しない。
2. **`amazon-backfill-no-amazon.tsv` に書いてはならない。** 同ファイルは「Amazon に同等品が存在しない」ことの台帳で、指標②の除外母数に使われる。「取得できなかった」を混ぜると母数が静かに歪む（§4-3 追補と同じ趣旨）。
3. **引き継ぎ場所は `claude/campkit-タスクキュー.md` の「## 取得できずに持ち越したカード」節。** 台帳に書ける列が無いので、キュー文書が唯一の引き継ぎ先とする。**監督が result を読んだサイクルで必ず 1 行追加する。**
4. 台帳・mdx は不変更（実行側は D-10 を維持）。**`verdict=blocked_by_amazon` は「ASIN を照合しようとして弾かれた」型を指すので、未設置カードの `/s` が弾かれた場合に書いてはならない。**

**適用（2 件）**: `sleeping-bag-temperature-guide#3#mthappy-down-mummy-25`（103 の Q3 が `bm-verify`・残り再試行 1 回）／`kids-sleeping-bag#1#kids-sb-rank-1`（104 の q1 が `bm-verify`・残り再試行 1 回・第1クエリ `Bears Rock MX-604J` から再開）。いずれもキュー文書の専用節に記録済み。

### 12-5. ★ 取得予算とアクセス制御の恒久ルール（第111回に条文化・2026-10-02）

**第104回〜第110回の運用で確定したが条文化していなかった3件を、ここに1本化する。**

#### 12-5-1. Amazon のアクセス間隔は「プロセスを跨いで」守る

1. **Amazon への連続アクセスの間隔は 90 秒以上とする。** `/s` と `/dp` を合わせて数える。
2. **★ 待機ロジックを同一プロセス内の変数だけに持たせてはならない。** 直前リクエスト時刻を**ファイルに永続化し、起動時に読む**こと。`/s` を CJS・`/dp` を ESM のように別プロセスで走らせると、同一プロセス内の変数では前回時刻が失われて間隔が壊れる（`campkit-20261002-M01` が「52 秒・20 秒の区間ができた」と自己申告した実例。`-M02`・`01`・`02`・`03` はスタンプファイル方式で是正し、`02` は別プロセス間でも実測 90,017 ms を達成した）。
3. **実測間隔（ミリ秒）を全リクエストぶん report の表に書く。**

#### 12-5-2. `bm-verify` を踏んだときの打ち切り手順

1. **`bm-verify` に当たったら、§12-2 の 4 点で「真のブロック」かを判定する。** バイト数の目安（2,282〜2,788）は**わずかに超えることがある**ので（2,800／2,886／2,996／3,177／3,408／4,244 B の実測あり）、**残り3点（`<title>` が空か `&nbsp;`／meta-refresh の `bm-verify`／`data-asin` 0 件）が揃えば真のブロックと扱ってよい。**
2. **真のブロックなら、言い換えクエリの投げ直しは1枚につき1本までとする。** 間隔は 90 秒以上で、**プロセスを跨ぐ場合は 12-5-1 のスタンプファイルで守る。**
3. 2本目も弾かれたら、そのカードは **§12-4 に従って結果を不使用とし、mdx・台帳を不変更で打ち切る。** `amazon-backfill-no-amazon.tsv` には書かない（§12-4 の 2.）。
4. **実ブラウザ相当のヘッダ（UA・`accept-language`・`accept`）を付けた1本だけの再試行は認める。** Cookie の偽装・ログイン状態の模倣はしない。
5. **観察（確証なし・判定に使わない）**: 3 語クエリが弾かれ 2 語に短縮したら通った回（`campkit-20261002-01`）と、3 語がそのまま通った回（`-02`・`-03`）の両方がある。**語数だけで決まるわけではないので、語数を根拠に「ブロックではない」と判断してはならない。**

#### 12-5-3. ASIN を新規設置／差し替えた行に `--judge` だけを当ててはならない

1. **`check-amazon-asin.cjs --judge` は fetch しない。** そのため `amazon_title`／`amazon_price` に前回の別 ASIN の監査証跡が残ったまま `price_gap` が再計算され、異常値になる（`campkit-20261002-01` の `camp-chair-highback#2` が `+3896%` になった実例）。
2. **ASIN を新規設置／差し替える回は、実取得した dp の保存 HTML を `HTML_DIRS[0]` に置き、`--only <slug>#<rank> --cached` を走らせて `amazon_title`／`amazon_price`／`amazon_stock` を同 dp の値に揃える**（Amazon アクセス 0 回）。出力に `Amazon アクセス 0 回` が出ることを確認する。
3. `--judge` を当てるのは、2. を済ませた**後**に限る。

#### 12-5-4. 楽天 API の予算とクエリの作り方

1. **監督がブランドを N 個名指しするタスクでは、楽天 API の予算を N＋1 以上にする。** 予算が N のままだと、最後のブランドに1クエリも投げられない（`campkit-20261002-01` が 5 ブランドを名指しされて予算 4 だったため、ロゴスを 1 クエリも投げられなかった実例）。**これは実行側の逸脱ではなく監督の設計不備である。**
2. **楽天 API のクエリは 3 語以内にする。** 4 語以上にすると該当 0 件に落ちやすい。
3. **1クエリ目は「ブランド語 ＋ カテゴリ語 ＋ 機能語」の棚卸しクエリにする。**
4. 楽天へのアクセス間隔は **8 秒以上**（Amazon の 90 秒とは別）。**§4-5 の既定（`availability=1` 等）を変えない。**

#### 12-5-5. 型の認定は検出器の出力を一次情報にする

1. **カードの型（型I／型I-b／型II）を認定するときは、`node scripts/check-card-name-vs-sku.cjs --only "<slug>#<rank>"` が出力する `brand`／`maker_model` を一次情報とする。**
2. **自作のパーサで楽天 item ページを解析して型を決めてはならない。** Joshin（`jism`）のような旧形式のページは EUC-JP で `brandName`／`makerModelNumber` という JSON キーを持たないため、自作パーサでは「ブランド欄なし＝型II」と誤認する余地がある。同スクリプトは同じページから `brand`／`maker_model` を構造フィールドとして正しく取れる（`campkit-20261002-02` §14-3 の申し送りを監督が実データで裏取りして採用した）。
3. 型の認定はスナップショットで固定せず、楽天 item ページを実取得して再確認する（§4-2 追補3 条文7）。

#### 12-5-6. 「点数・個数」の印字が同一 dp 内で食い違うときの扱い

1. **同一の dp に「セット点数」と「商品の個数」が別々に印字され、値が食い違うことがある**（`campkit-20261002-02` の実例: `t-サイズ: 5点セット` ↔ `t-商品の個数: 3`）。§11-15 は素材の粒度差だけを想定しており、この型を扱っていない。
2. **この場合は「カードが名指しする構成」と照合して、名指しに一致する側の値を正とする。** どちらも名指しに一致しないときは構成違い（§4-1 恒久ルール (A)）として採らない。
3. **採否の判断根拠を1行 report に残す。** 台帳の `note` にも同じ根拠を書く。

#### 12-5-7. Amazon の HTTP 429／503 スロットルは `bm-verify` とは別系統

1. **`/s` または `/dp` が HTTP 429 または 503 を返し、本文に `api-services-support@amazon.com` が印字されている場合は、Amazon 標準のスロットルページである。** `ref=cs_503_logo`／`ref=cs_503_link` の印字、`<title>` が `ご迷惑をおかけしています！`、`data-asin` が 0 件、本文が 2,100〜2,300 バイト程度、という組み合わせになる（`campkit-20261002-04` が `/s` 2 本連続で当たった実例）。
2. **この型には 12-5-2 の4点テストを当てない。** 4点のうち `bm-verify` の文字列と meta-refresh は立たないので、4点テストで判定しようとすると「ブロックではないかもしれない」と誤読する。**HTTP ステータスと本文の印字で判断して、その回の結果を直ちに不使用とする。**
3. **言い換えクエリの投げ直しは1枚につき1本まで**（12-5-2 条文2 と同じ）。2本目も 429／503 なら mdx・台帳を不変更で打ち切り、`amazon-backfill-no-amazon.tsv` には書かない（§12-4 の 2.）。**「取得できなかった」ことは「同等品が実在しない」ことの根拠にならない。**
4. `/s` が候補を1件も返せなかった回は `/dp` を開く対象が存在しないので、**`/dp` の予算は未使用のまま終えてよい。** 予算が残っていることは追加のクエリを投げてよい根拠にはならない。
